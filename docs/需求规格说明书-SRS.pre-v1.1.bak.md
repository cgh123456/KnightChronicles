## 0. 文档使用指引

### 0.1 与上游文档的关系

| 文档 | 回答的问题 | 变更频率 |

| PRD（`docs/PRD.md`） | 做什么游戏、为什么做、成功标准是什么 | 低（里程碑级） |

### 0.2 单条需求的固定结构

所有 `FR-xxx` 按以下 7 段展开（某些段不适用时标注「不适用」并说明原因）：

| 段 | 内容 | 目的 |
| --- | --- | --- |
| ① 需求头 | 编号 / 名称 / 优先级 / 交付里程碑 / 来源 / 依赖关系 | 排期与影响面分析 |
| ② 需求描述 | 一段话说明这条需求要达成什么 | 统一理解 |
| ③ 详细规则 | `R-x-x-x` 编号的原子规则，每条可独立判定真伪 | 消除歧义 |
| ④ 参数与公式 | 具体数值、计算公式、配置字段 | 可直接编码 |
| ⑤ 状态/流程 | 状态机、时序图或流程步骤 | 复杂逻辑的骨架 |
| ⑥ 边界与异常 | 异常输入 / 极端情况下的系统行为 | 防遗漏 |
| ⑦ 验收用例 | `TC-x-x-x` 编号的可执行用例 | 测试直接落地 |

### 0.3 三类读者的使用方式

- **程序**：读 ③④⑤⑥ 四段实现；⑦ 段用于自测。若 ③ 段某条规则无法判定真伪，该条需求视为不完整，需退回澄清。
- **测试**：⑦ 段直接转成测试用例；⑥ 段每条异常至少覆盖 1 个用例；数字精度的验收（如「偏差 ≤ 2%」）必须给出测量方法。
- **美术**：只需读 §3.1~§3.3 的表现相关规则、§3.10 音频需求、附录 A 数值基线表。

## 1. 引言

### 1.1 编写目的

将 PRD 中的产品愿景与用户故事拆解为**可开发、可测试、可验收**的逐条需求，作为代码开发与测试用例设计的唯一基线。PRD 回答"做什么游戏、为什么做"，本文档回答"每一项功能具体做到什么程度才算完成"。

### 1.2 范围

**In Scope**：MVP v0.5 至 v1.0 的全部功能需求、非功能需求、数据需求、接口需求。

**Out of Scope**（与 PRD §2.3 Non-Goals 一致，此处仅列出需求层面的含义）：

- 不定义联网同步协议、服务端接口、账号体系；
- 不定义移动端触屏交互与 UI 自适应布局；
- 不定义商业化（内购/广告）相关的埋点、支付、风控需求；
- 不定义 Mod 加载机制与外部资源热更（v2.0 评估）；
- v1.1+ 的需求仅在 §8 里程碑映射中列名，不展开设计。

### 1.3 术语与缩略语

| 术语 | 定义 |
| --- | --- |
| 单局 / Run | 从选角进入第 1 层到死亡或通关的完整过程 |
| 主题 / Theme | 一个关卡美术与怪物配置的集合，含 3 个普通层 + 1 个 Boss 层 |
| 层 / Floor | 一个主题内的一个地牢层，含 6–10 房间 + 层末出口 |
| 房间 / Room | 清怪开门的最小战斗/交互单元 |
| 关键路径 | 本层入口房到本层出口房之间的房间序列 |
| PCG | 程序化内容生成（Procedural Content Generation） |
| SO | Unity ScriptableObject 配置资产 |
| 无敌帧 / i-frame | 翻滚、受击后等期间免疫伤害的时间窗口 |
| 霸体 | 动作执行期间不因受击而中断 |
| 硬直 | 动作后摇期间无法接受新输入的状态 |
| DR | Damage Reduction，减伤系数 |
| 保底 | 连续未获得高稀有度物品时强制提升权重的机制 |
| 乘区 | 伤害计算中一个独立的乘法因子，同乘区内加法叠加 |
| 幂等 | 同一操作重复执行结果一致 |
| Seed / 种子 | PCG 随机数初始值，用于固定与复现生成结果 |

## 2. 总体描述

### 2.1 产品功能结构

```
骑士异闻录
├── 核心战斗（FR-1xx）
│   ├── 移动 / 瞄准 / 射击 / 翻滚 / 技能
│   ├── 伤害结算（含暴击 / 护盾 / 减伤）
│   ├── 敌人 AI（状态机）
│   ├── 弹幕系统（对象池 / 分层碰撞）
│   ├── Boss 战（阶段制）
│   └── 垂直维度机制（高度差判定）
├── 角色系统（FR-2xx）：选择 / 属性 / 解锁
├── 武器系统（FR-3xx）：配置 / 拾取切换 / 稀有度 / 分类
├── 天赋系统（FR-4xx）：三选一 / Buff 叠加
├── 关卡与生成（FR-5xx）：PCG / 房间流程 / 房间类型 / 层结构 / 种子 / 校验
├── 掉落与经济（FR-6xx）：掉落表 / 双货币 / 商店
├── 局外成长（FR-7xx）：宝石结算 / 解锁商店
├── UI / HUD（FR-8xx）：大厅 / HUD / 结算 / 暂停 / 设置
├── 存档（FR-9xx）：内容 / 原子写入 / 校验
└── 音频（FR-10xx）：BGM / 音效 / 混音分组
```

**模块依赖方向**（单向，禁止反向依赖与循环依赖）：

```
基础设施层（对象池 / 事件总线 / 异步加载 / 日志）
        ↑
数据层（ScriptableObject 配置 / JSON 存档）
        ↑
游戏逻辑层（战斗 / 状态机 / Buff / 房间流程）   ← 纯 C#，可单元测试
        ↑
表现层（GameObject / Animator / 粒子 / 相机 / 音频）  ← 只响应事件，不含规则
```

**跨模块硬约束**：

| 编号 | 约束 |
| --- | --- |
| R-2-1-1 | 逻辑层不得引用 `UnityEngine` 的表现相关命名空间（`Animator`、`ParticleSystem`、`AudioSource` 除外），以保证逻辑层可在无场景环境下单元测试 |
| R-2-1-2 | 表现层不得包含任何数值计算（伤害、掉落、概率），只能消费事件载荷 |
| R-2-1-3 | 配置数据只能通过 SO 读取，代码中不得出现影响平衡的硬编码数值 |
| R-2-1-4 | 全局随机数必须经统一 PRNG 服务获取，禁止直接调用 `UnityEngine.Random` 或 `System.Random`（保证 Seed 可复现，见 FR-505） |

### 2.2 运行环境与约束

| 项 | 内容 |
| --- | --- |
| 操作系统 | Windows 10 / 11 64 位（首要支持）；macOS 仅开发机自用，不列入交付验收 |
| 引擎 | Unity 2022.3 LTS + URP + C#（.NET Standard 2.1） |
| 输入 | 键鼠为主；手柄仅预留 Action Map（P2 实现） |
| 分辨率 | 16:9 为基准（1920×1080）；支持 1280×720 ~ 2560×1440 窗口化/全屏 |
| 网络 | **全程无网络通信**（见 NFR-106）；无账号体系 |
| 第三方依赖 | 无强制运行时依赖；DOTween 为可选项 |
| 合规约束 | 不收集任何用户数据；无内购即无支付合规负担 |

### 2.3 核心用户流程

**主流程（正常一局）**：

```
启动 → Boot（配置加载 / 对象池预热 / 存档读取）
      → Lobby（大厅：选角 / 解锁商店 / 设置）
      → [开始游戏] → Dungeon 生成第 1 层
      → 房间循环：进入房间 → 锁门 → 清怪 → 开门 → （奖励房/商店房/事件房可选）→ 下一房
      → 层结束 → 三选一天赋 → 进入下一层
      → 第 3 层结束 → Boss 房
      → Boss 战胜利
      → Result（结算：本局统计 + 宝石入账）→ [再来一局] → Dungeon 新局
                                        → [返回大厅] → Lobby
```

**关键分支**：

| 分支 | 触发 | 系统行为 |
| --- | --- | --- |
| 死亡 | 局内 HP ≤ 0 | 立即进入 Result，金币清零、宝石保留（FR-602） |
| 主动放弃 | 暂停菜单选「放弃本局」 | 与死亡同流程，但结算页标注"已放弃" |
| 存档损坏 | 启动时校验和失败 | 提示用户，可重建存档；有备份则恢复（FR-903） |
| 设置未保存 | 设置页直接关闭 | 自动保存；提供"恢复默认"（FR-805） |

### 2.5 全局设计约定

> 本节定义跨模块通用的计算约定。**所有需求中的数值判定与验收标准，若未特别声明，均遵循本节。**

**坐标系与单位**

| 项 | 约定 |
| --- | --- |
| 坐标系 | Unity 左手坐标系，Y 轴向上；地牢地面主平面为 `y = 0` |
| 长度 | 米（m） |
| 时间 | 秒（s），保留 3 位小数 |
| 速度 | 米/秒（m/s） |
| 角度 | 度（°），0° 指向世界 +Z，顺时针为正（俯视） |
| 帧率基准 | 60 FPS；1 帧 = 16.667 ms。所有「≤ N 帧」的验收在 60 FPS 下测 |

**距离判定约定**

| 编号 | 约定 |
| --- | --- |
| R-2-5-1 | 默认「距离」指 XZ 平面上的水平距离（忽略高度差），用于索敌、拾取、交互范围 |
| R-2-5-2 | 弹道命中判定使用真实 3D 距离，包含高度差 |
| R-2-5-3 | 涉及高度差的判定见 FR-110，阈值以「高度档位」表达而非连续值 |

**数值取整约定**

| 编号 | 约定 |
| --- | --- |
| R-2-5-4 | 伤害值：`floor` 取整，最小为 1（见 FR-106 公式第 6 步） |
| R-2-5-5 | 货币（金币/宝石）：整数，不允许小数 |
| R-2-5-6 | 概率与倍率：`double`，范围 [0, 1] 或 [0, +∞)，配置表中最多 3 位小数 |
| R-2-5-7 | UI 显示伤害/货币：伤害用整数，概率类展示为百分比且保留 1 位小数（如「暴击率 15.0%」） |

**随机数约定**

| 编号 | 约定 |
| --- | --- |
| R-2-5-8 | 全局 PRNG 由 `RandomService` 统一提供，分为三个独立流：`RunStream`（局内生成/掉落）、`CombatStream`（战斗判定如暴击/散布）、`CosmeticStream`（纯表现如粒子抖动），三者互不干扰 |
| R-2-5-9 | `RunStream` 的种子由玩家可见的 `RunSeed` 派生；同 `RunSeed` 必须产生完全相同的层结构、波次与掉落（FR-505） |
| R-2-5-10 | `CosmeticStream` 的变化不得影响 `RunStream` 与 `CombatStream` 的结果序列（防止加一个粒子效果就改变整局地图） |

**输入与响应约定**

| 编号 | 约定 |
| --- | --- |
| R-2-5-11 | 所有玩家输入在 `Update` 阶段的 Input System 回调中采样，禁止在 `FixedUpdate` 中读输入 |
| R-2-5-12 | 所有物理与命中判定在 `FixedUpdate`（默认 50 Hz）中执行 |
| R-2-5-13 | 「输入延迟」定义为：输入事件时间戳 → 对应可视/玩法结果首帧呈现时间戳（见 NFR-103 测量方法） |

**配置与文本约定**

| 编号 | 约定 |
| --- | --- |
| R-2-5-14 | 所有面向玩家的文本必须走文本表（FR/NFR-109），代码中禁止出现中文字符串字面量 |
| R-2-5-15 | 配置表数值越界时：编辑器加载阶段报错并拒绝进入 Play 模式；运行时构建中越界值被 `clamp` 到合法区间并记录警告日志 |

## 3. 功能需求详述（Functional Requirements）

### 3.1 核心战斗模块（FR-1xx）

#### FR-101 角色移动

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | Phase 0 |
| 来源 | PRD US3 / §2.4 |
| 依赖 | 无 |
| 被依赖 | FR-104（翻滚方向）、FR-107（敌人索敌）、FR-108（弹道起点） |

**② 需求描述**：玩家通过 WASD 控制角色在地面无惯性位移，斜向输入速度归一化，帧率波动下位移量保持一致。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-101-1 | 输入向量由 WASD 四键合成，取值范围为 8 个方向（含斜向），向量长度归一化后不得超过 1 |
| R-101-2 | 同时按下相反方向键（如 W+S）时，该轴输入为 0；四键全按视为无输入 |
| R-101-3 | 位移在 `FixedUpdate` 中按 `移速 × 帧时长` 积分，与渲染帧率解耦 |
| R-101-4 | 角色朝向在未射击时跟随移动方向；有输入即转向，转向为瞬时（无转身动画延迟影响碰撞体） |
| R-101-5 | 玩家移动不得穿过墙壁/掩体：使用 CapsuleCollider + 物理投射，禁止使用 `transform.position` 直接赋值 |
| R-101-6 | 移动状态下可同时射击（不互相阻塞），但翻滚期间不可移动（由翻滚控制位移） |
| R-101-7 | 启停响应为「近似即时」，但保留可调加速/减速参数，默认值为高速响应 |

**④ 参数与公式**

| 参数 | 默认值 | 配置位置 | 说明 |
| --- | --- | --- | --- |
| `baseMoveSpeed` | **5.0 m/s**【基线建议值】 | 角色表（FR-201） | 各角色基准移速 |
| `acceleration` | 60 m/s² | 角色表 | 达到全速所需约 0.083 s |
| `deceleration` | 80 m/s² | 角色表 | 停止所需约 0.063 s |
| `turnSpeed` | 1800 °/s | 全局常量 | 瞬时转向；防止 180° 突变导致视觉跳变 |

位移公式：

```
inputDir = normalize(WASD 合成向量)           # 长度 0 或 1
targetVelocity = inputDir × baseMoveSpeed × (1 + Σ移速加成)
currentVelocity = MoveTowards(currentVelocity, targetVelocity, accel/decel × fixedDeltaTime)
position += currentVelocity × fixedDeltaTime
```

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 键鼠断开 | 移动输入归 0，角色停下；不弹出阻断式弹窗（有暂停菜单可查） |
| 斜向撞墙 | 沿墙滑行（不解算为完全停止），滑行速度 = 投影分量 × 0.8 |
| 移速加成导致速度 > 20 m/s | `clamp` 至 20 m/s，记录警告日志（防止穿透地形） |
| 游戏窗口失焦 | 暂停游戏（见 FR-804），不接收输入 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-101-1 | 进入任意房间 | 按住 W 位移 5 s | 位移距离 = 5.0 × 5 = 25 m，误差 ≤ 1% |
| TC-101-2 | 同上 | 按住 W+D 位移 5 s | 总位移距离与 TC-101-1 偏差 ≤ 2%（归一化生效） |
| TC-101-3 | 同上 | 同时按 W 与 S | 角色不产生 Z 轴位移 |

#### FR-103 射击

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | Phase 0 |
| 来源 | PRD US3 / §2.4 |
| 依赖 | FR-102（方向）、FR-301（武器配置）、FR-108（弹幕） |
| 被依赖 | FR-106（伤害来源）、FR-304（逐武器冒烟测试） |

**② 需求描述**：按住鼠标左键持续射击，射速与弹道特性完全由当前武器配置驱动；近战类武器以挥砍弧替代弹丸。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-103-1 | 左键按下即发射第一发，之后按 `1 / fireRate` 的固定间隔连发，不依赖按住时长（首发起始不受间隔影响） |
| R-103-2 | 射速由武器 `fireRate`（发/秒）决定，连续射击的时间误差累计不得超过 ±5% |
| R-103-3 | 每次发射消耗 `energyCost` 蓝量；蓝量不足时发射失败，播「无能量」音效与 HUD 闪烁提示，**不自动切换武器** |
| R-103-4 | 弹匣制武器：弹匣打空后自动进入换弹（`reloadTime` 秒），换弹期间不可发射；换弹可被翻滚打断，翻滚后重新开始换弹 |
| R-103-5 | 散布：每发弹丸在瞄准方向的固定锥角内随机偏转，偏转角由 `CombatStream` 随机流生成（保证可复现） |
| R-103-6 | 近战武器不发射弹丸，改为在角色前方生成一个扇形攻击判定，扇形角度与半径由配置给定 |
| R-103-7 | 后坐力（可选，P1）：连发时相机产生幅度随 `recoil` 参数变化的偏移，停火后按 `recoilRecover` 速度回正 |
| R-103-8 | 切枪、翻滚、暂停、死亡状态下一律禁止发射 |

**④ 参数与公式**

| 参数 | 单位 | 说明 |
| --- | --- | --- |
| `fireRate` | 发/秒 | 射速；连发间隔 = `1 / fireRate` |
| `damage` | 点 | 单发基础伤害（见 FR-106） |
| `projectileSpeed` | m/s | 弹速；近战武器不适用 |
| `spread` | ° | 散布半锥角；每发偏转 = `spread × uniform(-1, 1)`（俯仰与偏航各一次） |
| `magazine` | 发 | 弹匣容量；0 表示无需换弹（如激光） |
| `reloadTime` | s | 换弹时长 |
| `energyCost` | 点/发 | 蓝量消耗 |
| `pelletCount` | 发 | 单次发射弹丸数（霰弹 > 1） |
| `range` | m | 射程；超过后弹丸销毁 |

近战扇形判定：

```
命中条件 = (目标与角色水平距离 ≤ meleeRange)
        AND (∠(角色朝向, 指向目标向量) ≤ meleeArc / 2)     # 俯视平面角度
```

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 蓝量恰好等于单发消耗 | 允许发射，发射后蓝量 = 0，下一次发射失败 |
| 换弹中死亡 | 换弹中断，结算页不反映换弹状态 |
| 射速配置为 0 或负数 | 配置校验阶段报错（FR-301 表校验），拒绝加载 |
| 弹丸在出生瞬间与自身碰撞 | 弹丸生成点位于角色碰撞体之外（`muzzleOffset` ≥ 0.5 m），且玩家弹与玩家碰撞层不互判 |
| 单帧内射出多发（fireRate > 帧率） | 按累积时间补偿，漏发在下一帧补射；单帧补射上限 3 发，超出丢弃并记警告 |
| 射程内无命中目标 | 弹丸抵达 `range` 后销毁并回收至对象池 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-103-1 | 装备 fireRate = 5 的武器 | 连射 60 s | 实际发射数 = 300 ± 5%（即 285–315 发） |
| TC-103-2 | 同上 | 单击左键 1 次（按下即松开） | 恰好发射 1 发 |
| TC-103-3 | 蓝量 = 1，单发耗能 = 1 | 连射 | 第 1 发成功，第 2 发失败并提示，蓝量 = 0 |
| TC-103-4 | 弹匣 = 10 | 连射至打空 | 自动换弹，换弹期间连续点击左键无弹丸射出 |
| TC-103-5 | 换弹中 | 按 Space 翻滚 | 换弹被打断计时归零，翻滚结束后重新开始换弹 |
| TC-103-6 | 输入延迟测量工具就绪 | 点击左键 | 从点击到弹丸出现的间隔 ≤ 100 ms（NFR-103） |
| TC-103-7 | 近战武器 | 面对正前方 1 m 处敌人挥砍 | 命中；侧后方 180° 的敌人不受伤 |

#### FR-104 翻滚

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | Phase 0 |
| 来源 | PRD US3 / §2.4 |
| 依赖 | FR-101（方向输入） |
| 被依赖 | FR-108（受击判定与无敌帧） |

**② 需求描述**：按 Space 触发带无敌帧的翻滚位移，是玩家规避弹幕的核心手段，其响应与判定精度直接影响战斗手感。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-104-1 | 按 Space 触发翻滚，无方向输入时翻滚方向 = 角色当前朝向；有输入时 = 输入方向 |
| R-104-2 | 翻滚总时长 0.35 s，其中 **0.30 s 为无敌帧**，剩余 0.05 s 为收势（仍不可被伤害打断但不免疫伤害） |
| R-104-3 | 翻滚期间为**霸体**：不因受击而中断翻滚动作 |
| R-104-4 | 冷却 1.5 s，从翻滚**开始时**计时；冷却中按 Space 无响应（不进入输入缓冲） |
| R-104-5 | 翻滚位移为固定距离的匀减速曲线，位移距离 3.5 m，与移速属性无关 |
| R-104-6 | 翻滚期间不可射击、不可使用技能、不可更换武器 |
| R-104-7 | 无敌帧内免疫一切伤害来源（弹丸、碰撞、接触伤害、Boss 大招地面持续伤害） |
| R-104-8 | HUD 提供冷却指示（环形进度），精度误差 ≤ 0.1 s；冷却完毕有明显的就绪反馈（音效 + 图标高亮） |
| R-104-9 | 翻滚结束时若仍按住移动键，立即恢复移动（无额外硬直） |

**④ 参数与公式**

| 参数 | 默认值【基线建议值】 | 说明 |
| --- | --- | --- |
| `dodgeDuration` | 0.35 s | 翻滚总时长 |
| `iFrameDuration` | 0.30 s | 无敌帧时长，从翻滚起始计算 |
| `dodgeCooldown` | 1.5 s | 冷却，从头计时 |
| `dodgeDistance` | 3.5 m | 总位移距离 |
| `dodgeSpeedCurve` | 前 15% 加速至峰值，后 85% 匀减至 0 | 位移曲线 |

位移曲线（归一化）：

```
t ∈ [0, 1]，t = 已过时间 / dodgeDuration
速度曲线 v(t) = peak × (1 - smoothstep(0.15, 1.0, t))
约束：∫v(t)dt = dodgeDistance（脚本启动时校验，误差 > 2% 时报配置错误）
```

**⑤ 状态机**

```
Idle ──[按 Space 且 CD 就绪]──> Dodging(0~0.35s)
  Dodging 内部：
    [0, 0.30s]  无敌帧开启，霸体开启，禁止射击/技能/换武器
    (0.30, 0.35s] 无敌帧关闭，其余限制保持
  Dodging ──[t ≥ 0.35s]──> Idle（CD 剩余 1.15s）
  Dodging ──[死亡判定]──> Dead（翻滚无法规避 HP ≤ 0 之外的状态，但无敌帧内不会扣血）
CD 计时独立于状态机运行，到期后无事发生（仅 HUD 状态变化）
```

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 冷却中连按 Space | 无响应、无音效、不缓存输入；HUD 保持冷却态 |
| 贴墙翻滚 | 位移被墙阻挡，位移距离缩短；无敌帧时长**不缩短**（保命能力不因地形打折） |
| 高台边缘翻滚 | 允许翻下（产生坠落），坠落过程是否保留无敌帧：**保留**（避免「翻下悬崖反而摔死」的负反馈） |
| 翻滚中游戏暂停 | 翻滚计时暂停；恢复后从断点继续 |
| 翻滚中按 Esc 放弃本局 | 正常进入结算 |
| 无敌帧恰好跨帧边界 | 无敌帧判定以累积时间戳比较，不按整帧计数，允许亚帧精度 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-104-1 | 空旷地面 | 按 Space，记录位移 | 位移距离 = 3.5 m ± 2% |
| TC-104-2 | 无输入 | 按 Space | 翻滚方向 = 当前角色朝向 |
| TC-104-3 | 按住 A | 按 Space | 翻滚方向 = 左（A 的方向） |
| TC-104-4 | 敌方弹丸飞来 | 在弹丸到达前 0.2 s 按 Space | 不受伤；弹丸穿过角色 |
| TC-104-5 | 同上 | 在弹丸到达前 0.32 s 按 Space | **受伤**（0.30 s 无敌帧已结束） |

| TC-104-7 | 翻滚中 | 被敌人攻击命中 | 翻滚动作不中断，但收势阶段（>0.30 s）会扣血 |

#### FR-106 伤害计算

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | Phase 0 |
| 来源 | PRD US3 |
| 依赖 | FR-301（武器配置）、FR-402（Buff） |
| 被依赖 | FR-107、FR-109、所有造成伤害的需求 |

**② 需求描述**：所有伤害（玩家→敌人、敌人→玩家、技能、持续伤害）走同一条结算管线，公式集中于逻辑层且只结算一次，结果可单元测试。这是全项目**最需要无歧义**的一条需求。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-106-1 | 全局唯一伤害入口：任何伤害必须经 `DamageSystem.Calculate(in DamageInput) → DamageOutput` 结算 |
| R-106-2 | 表现层严禁二次计算或修正伤害结果，只允许消费 `DamageOutput` 载荷 |
| R-106-3 | 计算按固定 6 步顺序执行，乘区之间为乘法，同乘区内为加法叠加 |
| R-106-4 | 伤害取整使用 `floor`，最终值下限为 1（防止 0 伤导致战斗死锁） |
| R-106-5 | 暴击判定使用 `CombatStream` 随机流，保证同 Seed 同结果 |
| R-106-6 | 护盾优先于生命值抵扣：护盾归零后溢出部分才扣 HP |
| R-106-7 | 无敌帧期间伤害判定为完全免疫（不扣护盾、不扣血、不触发受击表现），且不消耗暴击随机数（防止改变随机序列） |
| R-106-8 | 同一次攻击对同一目标的多次命中伤害独立结算（霰弹每颗弹丸独立） |
| R-106-9 | 持续伤害（DoT）按 `tickInterval` 分次结算，每次独立走管线 |

**④ 公式（权威定义）**

```
输入 DamageInput：
  baseDamage      基础伤害
  attackerBuffs   攻击方 Buff 汇总（提供 damageMultiplier 加成）
  critRate        暴击率        [0, 1]
  critMultiplier  暴击倍率      默认 2.0
  targetDR        目标减伤系数  [0, 0.9]
  targetShield    目标当前护盾
  targetHP        目标当前生命
  isWeakPointHit  是否命中弱点（P1，默认 false）

第 1 步  基础值           D0 = baseDamage
第 2 步  增益乘区（加法）  D1 = D0 × (1 + Σ attackerBuffs.damageMultiplier)
第 3 步  暴击乘区         D2 = D1 × (isCrit ? critMultiplier : 1.0)
                          isCrit = CombatStream.NextDouble() < critRate
第 4 步  弱点乘区（P1）    D3 = D2 × (isWeakPointHit ? 1.5 : 1.0)
第 5 步  目标减伤乘区      D4 = D3 × (1 - clamp(targetDR, 0, 0.9))
第 6 步  取整与下限        D_final = max(1, floor(D4))

护盾与生命分配：
  shieldAbsorb = min(targetShield, D_final)
  hpDamage     = D_final - shieldAbsorb
  newShield    = targetShield - shieldAbsorb
  newHP        = max(0, targetHP - hpDamage)

输出 DamageOutput：
  finalDamage / shieldAbsorbed / hpDamage / isCrit / isKillingBlow
  remainingHP / remainingShield / damageSource(武器ID或技能ID) / hitPoint
```

**护盾回复规则**（玩家侧，防滚雪球）：

| 规则编号 | 规则内容 |
| --- | --- |
| R-106-10 | 玩家护盾在**连续 3 s 未受击**后开始回复，回复速率 15 点/s |
| R-106-11 | 护盾回复上限为角色 `maxShield`，不溢出 |
| R-106-12 | 护盾回复期间若受击，回复中断并重新计时 3 s |
| R-106-13 | 无敌帧内未受击**计入**「未受击时间」（避免翻滚刷护盾被惩罚） |

**⑤ 结算时序**

```
[攻击方] 命中判定通过
   → 构造 DamageInput
   → DamageSystem.Calculate()          # 逻辑层，唯一一次结算
   → 应用结果到目标（护盾/HP）
   → 广播 OnEnemyDamaged / OnPlayerDamaged
   → [表现层] 数字化伤害、受击特效、震屏、音效（禁止修改数值）
   → 若 isKillingBlow → 广播 OnEnemyKilled → 掉落系统（FR-601）
```

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| `baseDamage` = 0 或负 | `D_final` 仍为 1（下限保护）；配置校验阶段对 0 伤害武器报警 |
| `critRate` > 1 或 < 0 | 配置校验阶段报错；运行时 `clamp` 至 [0, 1] |
| `targetDR` = 1（全免疫） | `clamp` 至 0.9，即最多减伤 90%，保证任何攻击都能造成伤害 |
| 一次伤害打空护盾并溢出 | 按上述分配公式处理，`shieldAbsorbed` + `hpDamage` = `finalDamage` |
| 目标已死亡后再次受击 | 忽略，不再结算，不广播事件 |
| 同一帧内多个伤害来源致死 | 第一个致死伤害触发 `OnEnemyKilled`，后续伤害被忽略（目标已标记死亡） |
| 无敌帧期间受击 | 完全免疫，伤害数字不显示，不触发受击音效与震屏 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-106-1 | 单调测试环境 | 输入 baseDamage=10，critRate=0，DR=0 | 输出 10 |
| TC-106-2 | 同上 | baseDamage=10，critRate=1，critMult=2.0 | 输出 20 |
| TC-106-3 | 同上 | baseDamage=10，DR=0.5 | 输出 5 |
| TC-106-4 | 同上 | baseDamage=1，DR=0.9 | 输出 `max(1, floor(0.1)) = 1` |
| TC-106-5 | 同上 | baseDamage=0 | 输出 1（下限保护） |
| TC-106-6 | 目标护盾=5，HP=100 | 造成 12 点伤害 | 护盾=0，HP=93，shieldAbsorbed=5，hpDamage=7 |
| TC-106-7 | 目标 HP ≤ 0 | 再次造成伤害 | 无变化，不广播二次击杀事件 |
| TC-106-8 | 玩家处于无敌帧 | 受 100 点伤害 | 护盾与 HP 均不变，无受击表现 |
| TC-106-9 | 玩家护盾=0，maxShield=50 | 静置 3 s → 再静置 2 s | 3 s 时开始回复，2 s 后护盾=30 |
| TC-106-10 | 同上 | 回复期间受击 | 回复中断，重新计时 3 s |
| TC-106-11 | 公式覆盖率统计 | 跑单元测试 | `DamageSystem` 分支覆盖率 100%，含全部边界值 |

#### FR-107 敌人 AI

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | Phase 0（1–2 种）→ MVP（≥8 种）→ v1.0（15 种） |
| 来源 | PRD §2.6、§3.2 |
| 依赖 | FR-101（玩家位置）、FR-106（伤害）、FR-108（弹幕） |
| 被依赖 | FR-109（Boss 阶段控制）、FR-502（房间清怪） |

**② 需求描述**：15 种普通怪物共享一套可配置的状态机框架，通过行为参数表区分行为差异，同屏活跃上限 25 个且无卡死。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-107-1 | 所有普通怪物共用同一状态机骨架，行为差异通过 `aiProfile` 配置实现，禁止为单种怪物写独立 AI 类 |
| R-107-2 | 状态机每 `aiTickInterval`（默认 0.1 s）评估一次转移条件，非每帧评估（性能考虑） |
| R-107-3 | 索敌使用 XZ 平面距离（R-2-5-1）与视线遮挡检查（有墙阻隔则丢失目标） |
| R-107-4 | 同屏活跃敌人总数 `clamp` 至 25；达到上限时新敌人延迟生成（在房间外排队），而非直接消失 |
| R-107-5 | 存在最大存活时间 `maxLifetime`（默认 120 s），超时后强制进入 `Dead` 并标记为「非击杀」（不掉落、不计入击杀数） |
| R-107-6 | 任何状态转换必须能在 1 小时内无死循环、无卡死 |
| R-107-7 | 怪物不得互相碰撞推挤导致挤出导航网格（使用软避让，禁止刚性碰撞） |
| R-107-8 | 受击后的硬直时长由 `hurtStunTime` 配置；硬直期间不可攻击，但可被连续击退（击退有上限，防止被推出地图边界） |

**⑤ 状态机（权威定义）**

```
                    ┌──────────────────────────────────────┐
                    ↓                                      │
  ┌──────────┐   发现玩家   ┌────────┐  进入攻击距  ┌──────────┐
  │ Patrol   │─────────────>│ Alert  │─────────────>│  Chase   │
  │ 巡逻     │              │ 警戒   │              │  追击    │
  └──────────┘              └────────┘              └──────────┘
       ↑                        │                        │
       │ 丢失目标 ≥ loseTime      │ 丢目标                 │ 到达射程
       │                        ↓                        ↓
       └────────────────────────┴──────────────────┌──────────┐
                                                   │ Attack   │
                    ┌──────────┐  攻击后摇结束     │  攻击    │
                    │ Recover  │<──────────────────└──────────┘
                    │  后摇    │
                    └──────────┘
                          ↑
        ┌─────────┐  受击  │
        │  Hurt   │───────┘（硬直结束后回到进入前的状态）
        └─────────┘
              ↑ 任意状态 HP ≤ 0
        ┌─────────┐
        │  Dead   │
        └─────────┘
```

| 状态 | 行为 | 转移条件与目标 |
| --- | --- | --- |
| `Patrol` | 在出生点 `patrolRadius` 内随机游走；不攻击 | → `Alert`：与玩家距离 ≤ `detectRadius` 且视线通畅 |
| `Alert` | 原地停顿，播放察觉动画/音效；不移动 | → `Chase`：停顿 `alertTime`（默认 0.4 s）后；→ `Patrol`：目标丢失 |
| `Chase` | 向玩家移动（寻路）；远程怪在 `preferredRange` 处停留 | → `Attack`：进入 `attackRange`；→ `Patrol`：丢失目标 ≥ `loseTime`（默认 3 s） |
| `Attack` | 执行攻击动作（近战挥击 / 远程发射 / 蓄力） | → `Recover`：攻击动作完成 |
| `Recover` | 后摇 `recoverTime`，不可再次攻击 | → `Chase`：后摇结束（若目标仍在射程）或 `Patrol`（目标已丢失） |
| `Hurt` | 硬直 `hurtStunTime`，被击退 | → 回到进入 `Hurt` 前的状态；若在 `Hurt` 期间再次受击，硬直计时重置 |
| `Dead` | 播放死亡表现，掉落结算，回收至对象池 | 终态 |

**④ 参数表（`aiProfile` 字段）**

| 字段 | 单位 | 说明 | 示例（近战小怪） |
| --- | --- | --- | --- |

| `loseTime` | s | 丢失目标判定时长 | 3.0 |

**③-1 碰撞矩阵（权威定义）**

| 弹丸层级 → 目标 ↓ | 玩家弹 | 敌弹 | 地形 |

**④ 参数表**

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `poolCapacity` | 500 | 对象池与同屏上限 |

**⑥ 边界与异常**

#### FR-109 Boss 战

| 项 | 内容 |
| --- | --- |
| 优先级 | P0（1 个灰盒 Boss）→ P1（5 个正式 Boss） |
| 交付里程碑 | Phase 0（灰盒）/ MVP（1 个）/ v1.0（5 个） |
| 来源 | PRD US2、§2.6 |
| 依赖 | FR-107（AI 框架）、FR-108（弹幕）、FR-106（伤害） |
| 被依赖 | FR-503（Boss 房间）、K1 成功标准 |

**② 需求描述**：每个 Boss 为脚本化阶段制战斗，阶段切换由血量阈值触发，技能按阶段解锁；所有大招必须给出提前量充足的可视预警，解决 3D 俯视角下的可读性问题。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-109-1 | 每个 Boss 至少 2 个阶段，阶段数由 Boss 表 `phaseCount` 配置 |
| R-109-2 | 阶段切换由血量百分比阈值触发（默认 100%→50%→0%，即 50% 处切阶段），阈值可配置 |
| R-109-3 | 阶段切换时播放固定演出（无敌 1.5 s + 动画 + 音效），演出期间 Boss 不受伤也不攻击 |
| R-109-4 | 每个阶段绑定一组技能，技能释放顺序可为随机或以 `skillWeights` 加权随机 |
| R-109-5 | **预警红线**：任何造成范围伤害或位移威胁的大招，必须提前 ≥ 0.8 s 给出落点指示或路径指示 |
| R-109-6 | 预警指示物必须在任意俯视角度与光照下清晰可见（与弹幕可读性红线同标准） |
| R-109-7 | Boss 战期间相机产生轻微推拉（放大 5%–10%），提升压迫感；相机变化不得影响瞄准精度（FR-102） |
| R-109-8 | Boss 战不允许「无限连招」：两次大招之间至少有 `skillGap`（默认 1.2 s）的可反应窗口 |
| R-109-9 | Boss 房的入口门在战斗开始后锁死，Boss 死亡后开启结算传送点（FR-502） |
| R-109-10 | Boss 死亡不可被跳过；若玩家在 Boss 战中死亡，则整局结束（无复活） |

**⑤ Boss 阶段状态机**

```
Enter ──[玩家进入 Boss 房]──> Intro（演出 2.0s，无敌，不可操作 Boss）
   └─> Phase1（技能组 A 循环）
        └─[HP ≤ 50%]─> Transition（演出 1.5s，无敌）──> Phase2（技能组 B 循环，攻击频率提升 20%）
             └─[HP ≤ 0%]─> Death（演出 3.0s，播放死亡动画 → 掉落 → 开启传送点）
```

**④ 参数表**

| 字段 | 单位 | 说明 | 基线建议值 |
| --- | --- | --- | --- |
| `phaseCount` | 个 | 阶段数 | 2（灰盒）/ 2–3（正式） |
| `phaseThresholds` | % | 阶段切换血量阈值 | [100, 50, 0] |
| `transitionInvulnTime` | s | 切换演出无敌时长 | 1.5 |
| `skillGap` | s | 大招最小间隔 | 1.2 |
| `warningLeadTime` | s | 预警提前量（**红线值，不得低于 0.8**） | 1.0 |
| `maxHP` | 点 | Boss 血量 | 3000–8000 |
| `cameraZoomIn` | % | 战斗时相机推近幅度 | 8 |

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 玩家在 Boss 战中死亡 | 立即进入结算，Boss 状态不再推进 |
| 玩家在切换演出期间攻击 Boss | 不造成伤害（无敌），且不打断演出 |
| 玩家在 Boss 房门口徘徊不进入 | 门保持开启（未触发战斗），Boss 保持 `Enter` 待机，不主动攻击 |
| 大招预警期间玩家逃离伤害范围 | 伤害正常结算但落空，不追击（预警是「可躲」的承诺） |
| 大招预警期间玩家死亡 | 立即结算，不播放后续大招 |
| 伤害一次跨越两个阶段阈值（如 60% → 45%） | 只触发一次阶段切换（跳过中间阶段，直接进入阈值对应阶段），不叠加演出 |
| Boss 卡入几何体 | 每 2 s 位置合法性检查，非法则复位至房中心 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-109-1 | 进入 Boss 房 | 观察 | 播放 2 s 入场演出，期间门锁死、Boss 无敌 |
| TC-109-2 | Boss HP 降至 50% | 观察 | 触发切换演出 1.5 s，之后技能组变更、攻击频率提升 |
| TC-109-3 | Boss 释放范围大招 | 用逐帧录制测量 | 落点指示先于伤害判定出现，提前量 ≥ 0.8 s |
| TC-109-4 | 同上 | 3 人盲测 | 指示物在任意视角下均可辨识，无「不知何时该躲」的反馈 |
| TC-109-5 | Boss 连续释放技能 | 测量间隔 | 任意两次大招之间的间隔 ≥ 1.2 s |
| TC-109-6 | Boss 战中玩家死亡 | 观察 | 立即进入结算，无残留 Boss 攻击 |
| TC-109-7 | 一次攻击从 60% 打到 45% | 观察 | 仅播放一次阶段切换演出 |
| TC-109-8 | Boss 死亡 | 观察 | 播放 3 s 死亡演出，掉落生成，传送点开启 |
| TC-109-9 | Boss 战全程 | 性能测量 | 帧率不低于基线 95% |

#### FR-110 垂直维度机制

| 项 | 内容 |
| --- | --- |
| 优先级 | **P1（是否进 MVP 待 PRD 评审确认，见 §9 待决问题 Q-1）** |
| 交付里程碑 | MVP 可选 / v1.0 |
| 来源 | PRD §2.5 第 2/3/4 项 |
| 依赖 | FR-101（移动）、FR-108（弹道） |
| 被依赖 | FR-501（房间模块需支持立体模块） |

**② 需求描述**：引入高度差概念，使高台、悬崖、低位掩体具备真实的空间语义，是本作相对 2D 玩法参照的核心差异点之一。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-110-1 | 高度差不使用连续值判定，采用**离散高度档位**（默认 3 档：低 0 m / 中 2 m / 高 4 m），保证判定可预测、可测试 |
| R-110-2 | 角色可以自由走下低高度差（≤ 1 档，即 ≤ 2 m）；跨 2 档（4 m）需走楼梯/斜坡等连接体 |
| R-110-3 | 直接走下超过 1 档的高度差不造成伤害（避免惩罚性设计），但产生落地硬直 0.3 s |
| R-110-4 | 掩体阻挡规则：弹道只能被**高度 ≥ 弹道起始高度**的掩体阻挡 |
| R-110-5 | 高台角色可越过低位掩体射击低位目标；低位角色无法越过同一掩体射击高台目标 |
| R-110-6 | 投掷物使用抛物线，可通过高抛越过高度不超过其弹道最高点的掩体（FR-108 R-108-8） |
| R-110-7 | 垂直遮挡不得破坏可读性红线（PRD §2.5 第 8 项）：立体结构禁止遮挡交战区域核心视线；高台边缘必须有轮廓光/描边区分 |
| R-110-8 | 小地图（FR-802）以楼层色阶区分高度档位，玩家始终可见自身所在档位 |
| R-110-9 | 敌人 AI 在垂直场景中需支持「同档位寻路」；跨档位追击需经连接体（不允许敌人直接跳下追击，重型怪尤其） |

**④ 参数表**

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `heightTiers` | `[0, 2, 4]` m | 高度档位定义 |
| `walkDownMaxTier` | 1 | 可直接走下的最大档位数 |
| `landingStunTime` | 0.3 s | 落地硬直 |
| `throwArcHeight` | 3.0 m | 手雷类弹道最高点（可越 2 m 掩体） |

**豁免规则（重要）**：

```
弹道被掩体阻挡的判定：
  if (掩体高度档位 ≥ 弹道起始点高度档位) → 阻挡
  else → 不阻挡（弹丸从上方掠过）
```

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 角色站在高台边缘向下射击 | 弹道按 3D 方向计算，命中低处目标；准星落在低处地面（R-102-3 已覆盖） |
| 低处角色射击高台目标 | 弹丸被高台边缘阻挡（除非角度能越过边缘线） |
| 角色卡在两档之间（斜坡上） | 高度档位取最近档位；判定使用角色碰撞体中心高度 |
| 高台被完全遮挡视线（违反 R-110-7） | 视为关卡设计错误，PCG 校验阶段拒绝该房间模块（FR-506） |
| 敌人不会下高台追击 | 敌人转 `Patrol`；若玩家持续在高台下攻击，敌人以远程手段反击（远程怪）或原地等待（近战怪） |
| 玩家翻滚下高台 | 允许；落地硬直期间不可操作（0.3 s），无敌帧已结束则可能被打 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-110-1 | 站在 2 m 高台 | 走向边缘并走下 | 正常落地，产生 0.3 s 硬直，不扣血 |
| TC-110-2 | 站在 4 m 高台边缘 | 直接走下 | 允许，落地硬直 0.3 s（无伤害） |
| TC-110-3 | 高台（2 m）玩家，枪口高度 2 m | 向低处（0 m）**1 m 高**掩体后的敌人射击 | 命中（掩体高度 1 m < 弹道起始 2 m，不阻挡） |
| TC-110-3b | 高台（2 m）玩家，枪口高度 2 m | 向低处（0 m）**2 m 高**掩体后的敌人射击 | **被阻挡**（掩体高度 2 m ≥ 弹道起始 2 m，按 Q-2 口径「≥ 即阻挡」） |
| TC-110-4 | 高台（4 m）玩家 | 向低处 2 m 掩体后敌人射击 | 命中（掩体高度 2 m < 弹道起始 4 m） |
| TC-110-5 | 低处（0 m）玩家 | 向 2 m 高台上的敌人射击 | 被高台边缘阻挡，除非射线越过边缘 |
| TC-110-6 | 角色携带手雷 | 向 2 m 掩体后的敌人投掷 | 抛物线越过掩体并命中 |
| TC-110-7 | 垂直关卡 | 3 人盲测 | 交战区域核心视线无遮挡；高台边缘可辨识 |
| TC-110-8 | 敌人在高台上 | 玩家下到低处 | 近战怪不跳下追击；远程怪可远程攻击 |
| TC-110-9 | 1000 层 PCG 校验 | 运行 | 无「高层完全遮挡交战区」的房间被采用 |

> **口径说明**：TC-110-3 与 TC-110-3b 是一对边界用例，用来锁定「掩体高度恰好等于弹道起始高度」时的判定结果。当前取 **「≥ 即阻挡」**（对防守方有利、更符合玩家直觉），因此 TC-110-3b 的预期为「被阻挡」。该口径需在评审中确认，见 §9.2 待决问题 Q-2。

#### FR-202 角色属性

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | MVP |
| 来源 | PRD US1 |
| 依赖 | FR-106（护盾/HP 结算）、FR-101（移速） |
| 被依赖 | FR-201、FR-402（Buff 修改属性） |

**② 需求描述**：角色基础属性由配置表驱动，并与天赋/Buff 的修饰值正确叠加，属性变化可被任意模块实时查询。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-202-1 | 基础属性存储在角色 SO；运行时属性 = 基础值 + Buff 修饰，查询走统一入口 `StatProvider.Get(StatType)` |
| R-202-2 | 属性类型全集（v1.0）：移速、最大HP、最大护盾、最大蓝量、伤害加成、暴击率、暴击伤害、护盾回复速率、冷却缩减 |
| R-202-3 | 属性修饰分三种模式：`Add`（加法，如 +10 点最大HP）、`MulAdd`（加法乘区，如 +15% 伤害）、`Override`（覆盖，仅用于特殊机制） |
| R-202-4 | 属性计算顺序：先 `Add` 后 `MulAdd`，`Override` 优先级最高；同一属性同模式的所有来源相加 |
| R-202-5 | 属性变更必须广播 `OnStatChanged`，使 HUD（血条上限等）实时更新 |
| R-202-6 | 最大 HP 提升时，当前 HP 按等比例补偿（避免升级后「血量看着涨了实际没回」）；最大 HP 下降时，当前 HP `clamp` 至新上限 |
| R-202-7 | 局内属性（含 Buff 修饰）在死亡/结算时全部清零，只保留基础值 |

**④ 公式**

```
finalStat = Override ?? (baseStat + Σ Add) × (1 + Σ MulAdd)
clamp 规则：
  移速              ∈ [1.0, 20.0] m/s
  最大HP            ≥ 1
  最大护盾          ≥ 0
  最大蓝量          ≥ 0
  暴击率            ∈ [0, 1]
  暴击伤害倍率      ∈ [1.0, 10.0]
  冷却缩减          ∈ [0, 0.6]        # 上限 60%，防止技能零冷却
  伤害加成          ∈ [-0.9, +5.0]    # 下限保证至少 10% 伤害（与 FR-106 R-106-3 呼应）
```

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 冷却缩减累加至 100% | `clamp` 至 60%（防止技能无冷却导致卡死或数值失控） |
| 伤害加成降至 -100% | `clamp` 至 -90%，配合 FR-106 的 `max(1, ...)` 保证仍有伤害 |
| 同一天赋叠加多次 | 按 `MulAdd` 累加；若天赋配置为「不可叠加」，由 FR-402 拦截 |
| 最大 HP 下降到低于当前 HP | 当前 HP `clamp` 至新上限，不产生负数 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-202-1 | 无 Buff | 读取 9 项属性 | 与角色表完全一致 |
| TC-202-2 | 装备 +15% 伤害、+10 点最大HP 两个天赋 | 读取属性 | 伤害加成 0.15，最大HP = 基础 + 10 |
| TC-202-3 | 同上，再叠加一层 +15% 伤害 | 读取伤害加成 | 0.30（MulAdd 相加） |
| TC-202-4 | 最大HP 从 120 提升至 150，当前 HP = 60 | 观察当前 HP | 按比例提升至 75 |
| TC-202-5 | 冷却缩减叠加至 80% | 读取 | 0.60（clamp 生效） |
| TC-202-6 | 单局死亡 | 进入新局 | 属性回到基础值，无残留加成 |

#### FR-402 Buff 叠加

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | MVP |
| 来源 | PRD US5 |
| 依赖 | FR-202（属性系统） |
| 被依赖 | FR-105（技能增益）、FR-401（天赋）、FR-106（伤害加成） |

**② 需求描述**：所有增益与减益（天赋、技能、临时效果）经统一 Buff 系统管理，叠加规则逐条可配置且行为可预测。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-402-1 | Buff 与天赋共用同一套修饰机制；天赋 = 永久型 Buff（`duration = ∞`，随局结束清除） |
| R-402-2 | 每个 Buff 实例包含：`buffId`、来源、修饰列表（属性 + 模式 + 值）、剩余时长、叠加层数 |
| R-402-3 | 叠加策略按 `stackPolicy` 配置：`Stack`（层数叠加，效果 × 层数）、`Refresh`（刷新时长，效果不叠加）、`Max`（取最大值）、`Mutex`（互斥，新覆盖旧） |
| R-402-4 | 同 `buffId` 的叠加受 `maxStack` 限制，超出后按 `Stack` 策略丢弃或按 `Refresh` 刷新 |
| R-402-5 | 时效型 Buff 在游戏暂停时计时暂停（与 FR-805 一致） |
| R-402-6 | Buff 增删必须广播 `OnBuffChanged`，使 HUD 的 Buff 图标区实时更新 |
| R-402-7 | 死亡/结算/新局开始时，全部 Buff 无条件清空 |
| R-402-8 | Buff 修饰不得绕过 FR-202 的 `clamp` 规则 |

**⑤ 叠加策略对照表**

| 策略 | 同 Buff 再次获得 | 适用场景 |
| --- | --- | --- |
| `Stack` | 层数 +1，总效果 = 单层效果 × 层数 | 锐利、铁壁等可叠加天赋 |
| `Refresh` | 时长重置为满值，效果不叠加 | 临时增益（如「击杀后 3 s 射速 +25%」） |
| `Max` | 取效果更强的一个 | 同类减益（如多种减速取最强） |
| `Mutex` | 新的替换旧的 | 互斥组天赋 |

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 同一 Buff 在同一帧内被添加两次 | 按策略处理，不得出现「层数涨 2 但只结算 1」的中间态 |
| 时效 Buff 剩余时长恰好为 0 | 该帧结束时移除，不产生负时长 |
| 移除 Buff 时属性回退到负值 | 按 FR-202 的 `clamp` 处理 |
| 互斥组内两个天赋都存在（存档异常） | 加载时只保留权重高的一个，并记警告 |
| Buff 数量极多（>100） | 属性计算缓存结果，仅在 Buff 变更时重算，避免每帧全量求和 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-402-1 | 叠加「锐利」3 层 | 读取伤害加成 | +36%（12% × 3） |
| TC-402-2 | 获得 `Refresh` 型临时 Buff | 在剩余 1 s 时再获得 | 时长重置为满值，效果不叠加 |
| TC-402-3 | 同名减益减速 20% 与 30% | 同时获得（`Max` 策略） | 实际减速 30% |
| TC-402-4 | 互斥组两个天赋（异常构造） | 加载存档 | 仅保留权重高者，并输出警告日志 |
| TC-402-5 | 添加 100 个 Buff | 测量性能 | 属性计算耗时 ≤ 0.1 ms/帧（缓存生效） |

| TC-402-7 | 单元测试 | 跑完整测试集 | 叠加逻辑分支覆盖率 ≥ 90% |

### 3.5 关卡与地牢生成（FR-5xx）

#### FR-501 PCG 地牢生成

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | MVP |
| 来源 | PRD US6 / §3.1 |
| 依赖 | 房间模块表、主题表（§5.1） |
| 被依赖 | FR-502/503/504/505/506 |

**② 需求描述**：每层地牢由程序化生成，保证结构连通、无重叠、可通过，并支持种子复现。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-501-1 | 生成分三阶段：**房间布局** → **类型指派** → **走廊连接与实例化**，任一阶段失败则整层重新生成 |
| R-501-2 | 房间布局使用网格化放置，每个房间占 `1×1` 或 `2×2` 网格单元；房间之间不得重叠 |
| R-501-3 | 房间数量 `roomCount` ∈ [6, 10]，由 `RunStream` 随机流决定 |
| R-501-4 | 起点房（层入口）与终点房（层出口，Boss 层为 Boss 房）由类型指派阶段固定标记 |
| R-501-5 | 走廊连接必须保证起点到终点 100% 连通（生成后执行连通性断言，失败则重生成） |
| R-501-6 | 房间从当前主题的模块池中实例化（FR-503），模块出入口方向必须与走廊方向匹配 |
| R-501-7 | 生成耗时预算：单层 ≤ 300 ms（不含资源加载） |
| R-501-8 | 生成过程中允许重试，单层最大重试 20 次；超过则使用保底线性布局并记录警告 |
| R-501-9 | 保底布局：所有房间强制排成一条直线，保证可通关（牺牲随机性换取不卡关） |

**⑤ 生成流程**

```
[1] 布局阶段
    随机 roomCount ∈ [6,10]
    在网格上随机放置房间（从起点向外扩散），冲突则重试该房间
    ↓
[2] 类型指派阶段
    标记起点房 / 终点房（Boss 层标记 Boss 房）
    按配比表（FR-503）指派战斗/奖励/商店/事件房
    断言：奖励房 ≥ 1、商店房 ≥ 1、事件房 ≥ 1
    ↓
[3] 连接阶段
    用生成树算法（Prim/Kruskal 变体）连接全部房间 → 保证连通
    可选：额外添加 1–2 条环路，减少「死胡同感」（不影响关键路径长度断言）
    ↓
[4] 校验阶段
    连通性断言（起点→终点可达）
    重叠断言（无房间重叠）
    关键路径长度断言（∈ [6,14]，见 Q-5）
    失败 → 回到 [1] 重试（最多 20 次）
    ↓
[5] 实例化阶段
    按房间类型从模块池取模块 → 匹配出入口 → 拼接 → 放置怪点/掉落点
```

**④ 参数表**

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `roomCountRange` | [6, 10] | 单层房间数范围 |
| `gridSize` | 32 × 32 | 布局网格 |
| `maxRetry` | 20 | 单层最大重试次数 |
| `generationBudget` | 300 ms | 单层生成耗时预算 |
| `extraLoops` | [1, 2] | 额外环路数量 |
| `keyPathRange` | [6, 14] | 关键路径长度约束（见 Q-5） |

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 20 次重试均失败 | 启用保底线性布局，记录警告日志（含 Seed），游戏继续 |
| 网格空间不足以放置 6 个房间 | 扩大网格尺寸至 48×48 再试；仍不足则走保底布局 |
| 主题模块池中缺少某类型的模块 | 配置校验阶段报错（`主题表` 必须为每类房间提供 ≥ 3 个模块） |
| 生成耗时超过 300 ms | 记录警告；不中断生成（宁可慢也不能出坏图） |
| 存在孤立房间（无法连通） | 该房间被标记为「不生成」，重新连接其余房间 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-501-1 | 校验工具就绪 | 批量生成 1000 层 | 起点→终点连通率 100% |
| TC-501-2 | 同上 | 检查房间摆放 | 房间重叠次数 = 0 |
| TC-501-3 | 同上 | 统计房间数 | 全部 ∈ [6, 10] |
| TC-501-4 | 同上 | 统计关键路径长度 | 全部 ∈ [6, 14]（若与房间数约束冲突，见 Q-5） |
| TC-501-5 | 同上 | 统计生成耗时 | 单层 ≤ 300 ms（P95） |

| TC-501-7 | 1000 层生成 | 核对类型配比 | 每层奖励/商店/事件房各 ≥ 1 |

#### FR-502 房间流程

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | MVP |
| 来源 | PRD US2 |
| 依赖 | FR-107（清怪判定）、FR-109（Boss 房） |
| 被依赖 | FR-401（层结束触发）、FR-802（小地图） |

**② 需求描述**：房间采用「进入锁门 → 清怪 → 开门」的经典流程，门状态机必须严格无非法跳变，且不允许漏怪导致卡门。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-502-1 | 玩家进入房间触发区域后，房间门关闭，房间标记为「战斗中」 |
| R-502-2 | 门有且仅有三种状态：`Open` / `Locked` / `Sealed`，状态转换必须经唯一入口 `RoomDoor.SetState()` |
| R-502-3 | 清怪判定：本房间内所有「归属于本房间」的敌人均死亡后开门 |
| R-502-4 | 非战斗房（奖励/商店/事件）不锁门，不触发战斗 |
| R-502-5 | 漏怪保护：房间标记为战斗中但 3 s 内未检测到任何存活敌人，则强制开门并记录警告（防卡门） |
| R-502-6 | 已清空的房间再次进入不重新刷怪，门保持 `Open` |
| R-502-7 | Boss 房清空后不生成普通出口门，改为生成结算传送点 |
| R-502-8 | 房间状态（是否已清）写入本局运行时数据，用于小地图展示 |
| R-502-9 | 玩家在门关闭时有 0.5 s 的「门动画缓冲期」，期间仍可离开（避免被门夹住） |

**⑤ 门状态机**

```
                玩家进入触发区
   Open ─────────────────────────> Locked（门关闭动画 0.5s，含缓冲期）
     ↑                                  │
     │ 清怪完成 / 漏怪保护触发              │ 玩家尝试穿越
     │                                  ↓
     └─────────────────────────── Sealed（完全封闭，不可穿越）
                                        │
   Sealed ──[清怪完成]──> Locked（开门动画）──> Open（可通行）
```

| 状态 | 语义 | 允许穿越 |
| --- | --- | --- |
| `Open` | 门开启 | ✅ |
| `Locked` | 门关闭但处于动画缓冲期 | ✅（0.5 s 内） |
| `Sealed` | 门完全封闭 | ❌ |

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 敌人生成失败（一只都没生成） | 3 s 后强制开门（R-502-5） |
| 敌人被击退出房间 | 仍归属本房间，需被击杀；若被击出后长时间不回，2 s 后传回 |
| 玩家在门关闭瞬间翻滚穿门 | 门使用碰撞体阻挡，禁止穿越（翻滚不穿越锁门） |
| 房间内有可破坏物但无敌人 | 直接开门（可破坏物不计入清怪条件） |
| 玩家同时触发相邻两房间 | 房间按触发顺序依次处理，不并行锁门 |
| Boss 房玩家死亡 | 进入结算，Boss 房状态不再变化 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-502-1 | 进入战斗房 | 观察 | 门关闭并锁死，无法离开 |
| TC-502-2 | 击杀全部敌人 | 观察 | 门开启并可通行 |
| TC-502-3 | 构造「不生成敌人」的房间 | 进入 | 3 s 后门强制开启，日志有警告 |
| TC-502-4 | 已清空的房间 | 再次进入 | 不重新刷怪，门保持开启 |
| TC-502-5 | 房间战斗中 | 逐帧监控门状态 | 状态转换只经 `Open→Locked→Sealed→Locked→Open` 合法序列，无非法跳变 |
| TC-502-6 | 门关闭动画期间（0.5 s 内） | 走向门 | 可通行 |
| TC-502-7 | 门 `Sealed` 状态 | 尝试翻滚穿越 | 被阻挡 |

#### FR-503 房间类型

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | MVP |

| 依赖 | FR-501、FR-502 |
| 被依赖 | FR-603（商店房）、FR-601（奖励房掉落） |

**② 需求描述**：四类房间按配比表分布，保证每层至少各有一个奖励房与商店房，形成可预期的资源节奏。

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-503-1 | 四类房间：战斗房、奖励房、商店房、事件房（+ 起点房、终点房、Boss 房为特殊类型） |
| R-503-2 | 每层奖励房 ≥ 1、商店房 ≥ 1、事件房 ≥ 1（PRD §3.2 硬性断言） |
| R-503-3 | 剩余房间全部为战斗房 |
| R-503-4 | 类型指派需满足配比表（下表），并保证关键路径上至少有 2 个战斗房（避免一路白给） |
| R-503-5 | 起点房与终点房不计入四类统计 |
| R-503-6 | 分配算法：先满足最低配额（各 1 个），剩余名额按权重随机分配为战斗房 |

**④ 配比表（按房间总数，权威口径）**

**口径定义**：起点房与终点房是房间总数**之内**的两个房间（`class` 分别为 `Start` / `End`），不计入四类功能性房间的统计。

| 房间总数 | 起点房 | 终点房 | 战斗房 | 奖励房 | 商店房 | 事件房 | 合计 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 6 | 1 | 1 | 1 | 1 | 1 | 1 | 6 |
| 7 | 1 | 1 | 2 | 1 | 1 | 1 | 7 |
| 8 | 1 | 1 | 3 | 1 | 1 | 1 | 8 |
| 9 | 1 | 1 | 3 | 2 | 1 | 1 | 9 |
| 10 | 1 | 1 | 4 | 2 | 1 | 1 | 10 |

> **⚠️ 本表暴露的冲突**：`房间总数 = 6` 时，扣除起点与终点后只剩 4 个房间，而奖励/商店/事件房各需 1 个，仅剩 1 个战斗房 —— 这**违反 R-503-4「关键路径上至少 2 个战斗房」**。该冲突的解法（复合房 / 提高最小房间数 / 放宽战斗房下限）尚未确定，列入 §9.2 待决问题 **Q-6**。**在 Q-6 有结论前，`roomCount = 6` 的生成配置不应启用**。

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 房间数 = 6，需求恒定占 6 个 | 战斗房只剩 1 个；需满足 R-503-4「关键路径至少 2 个战斗房」可能冲突 → 此时提高房间数至 7 或降低最低配额，列入 Q-6 |
| 事件房模块池为空 | 配置校验阶段报错 |
| 某类型房间被指派到死胡同 | 允许，但奖励房/商店房优先指派在关键路径或靠近终点 |

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-503-1 | 1000 层生成 | 统计每层房间类型 | 每层奖励房 ≥1、商店房 ≥1、事件房 ≥1，通过率 100% |
| TC-503-2 | 同上 | 核对配比 | 各类数量与配比表一致 |
| TC-503-3 | 同上 | 检查关键路径 | 关键路径上战斗房 ≥ 2 |
| TC-503-4 | 房间总数 = 6 的层 | 检查 | 各类型恰好 1 个（含起点/终点） |

**掉落基线（**待数值评审**）**：

| 事件 | 掉落内容 | 期望值 |
| --- | --- | --- |
| 普通怪死亡 | 金币 3–8；概率 2% 掉消耗品 | 单层约 150–250 金币 |
| 宝箱（奖励房） | 武器 ×1（按稀有度权重）；宝石 5–15 | 每层 1 个 |
| 精英怪死亡（10% 概率出现） | 武器 ×1；宝石 3–10 | — |
| Boss 死亡 | 武器 ×1（保底紫色以上）；宝石 20–40 | 每个 Boss |
| 事件房奖励 | 按事件脚本定义 | — |

单局期望宝石产出：普通掉落 + 宝箱 + Boss ≈ **30–60 宝石**（对应 FR-702 解锁费用 800–1600，即 13–53 局解锁一个角色 —— 需在评审中确认该节奏是否合适，列入 §9 待决问题 Q-7）。

**⑤ 保底流程**

```
每层结束时检查：
  if (本层掉落中出现 ≥ 紫) → pityCounter = 0
  else → pityCounter += 1
  if (pityCounter ≥ pityThreshold) → 下一层起：紫/橙权重 × pityMultiplier
  掉出紫以上后立刻：pityCounter = 0，权重倍率恢复 1.0
```

**⑥ 边界与异常**

| 场景 | 系统行为 |
| --- | --- |
| 掉落位置在墙内 | 向房间中心方向逐步回退搜索最近合法点，最多尝试 10 次；失败则改在房间中心生成 |
| 同屏掉落物 > 50 | 最旧的自动消失（防性能问题） |
| 保底触发后仍连续未掉紫 | 权重倍率保持累计（不叠加，固定 ×2.0），保证概率显著提升 |
| 权重表全部为 0 | 配置校验失败 |
| 事件房脚本要求掉落不存在的物品 | 跳过该掉落并记错误日志 |

#### FR-902 原子写入

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 交付里程碑 | MVP |
| 来源 | PRD US7 / §4.2 |
| 依赖 | FR-901 |

**③ 详细规则**

| 规则编号 | 规则内容 |
| --- | --- |
| R-902-1 | 写入流程固定为四步：写临时文件 → 刷盘（`Flush`/`fsync` 等价） → 原子替换 → 删除临时文件 |
| R-902-2 | 临时文件命名：`slot0.json.tmp`；替换使用文件系统原子操作（`File.Replace` 或 `Move` 覆盖） |
| R-902-3 | 替换前保留一份上一版本为 `slot0.json.bak`，供恢复使用 |
| R-902-4 | 任何一步失败都不得破坏原存档 |
| R-902-5 | 写入过程不得阻塞主线程超过 1 帧；大文件写入走异步 |
| R-902-6 | 同一存档的并发写入必须串行化（加锁或队列），禁止并发写同一文件 |

**⑤ 写入流程**

```
[1] 序列化为 JSON 字符串
[2] 计算 checksum，写入 checksum 字段
[3] 写入 slot0.json.tmp（完整写入 + Flush + Close）
[4] 校验 tmp 文件可被解析（回读校验）
[5] 将现有 slot0.json 重命名为 slot0.json.bak（若存在）
[6] 将 slot0.json.tmp 原子替换为 slot0.json
[7] 删除或保留 .bak（保留最近一份）
失败处理：任一步失败 → 原 slot0.json 保持不动，报错返回 false
```

**⑦ 验收用例**

| 用例编号 | 前置 | 操作 | 预期 |
| --- | --- | --- | --- |
| TC-902-1 | 存档写入过程中 | 强杀进程 100 次（在写入的不同时间点） | 存档损坏率 = 0；每次重启都能读到有效存档（旧值或新值） |
| TC-902-2 | 模拟第 [4] 步回读校验失败 | 触发写入 | 写入失败返回 false，原存档完好 |
| TC-902-3 | 模拟磁盘满 | 触发写入 | 写入失败，原存档完好 |
| TC-902-4 | 同帧触发两次写入 | 观察 | 两次写入串行执行，无交织 |
| TC-902-5 | 明文观察 | 检查目录 | 写入完成后无残留 .tmp 文件 |

### 6.3 场景清单与加载流程

| 场景 | 用途 | 内容 |
| --- | --- | --- |
| `Boot` | 初始化 | 配置加载 → 对象池预热 → 存档读取与校验 → 硬件探测 → 跳转 Lobby |
| `Lobby` | 大厅 | 选角 / 解锁商店 / 设置 / 退出 |
| `Dungeon` | 地牢运行时 | PCG 动态构建（**单场景复用**，层间不重载场景） |
| `Result` | 结算 | 叠加层（overlay），不重载 `Dungeon` |

**加载流程**

```
Boot
 ├─ 加载全部 SO 配置（+ 校验，失败则阻断并报错）
 ├─ 对象池预热（弹丸 300 / 特效 100 / 伤害数字 50）
 ├─ 读取存档 → 校验和验证 → 迁移 → 填充运行时数据
 ├─ 硬件探测 → 给出画质推荐值
 └─ 异步加载 Lobby

Lobby ──[开始游戏]──> 异步加载 Dungeon（预加载主题 1 资源）
                       └─ 生成第 1 层（FR-501，≤300ms）
                          └─ 进入首房（总耗时 ≤3s，NFR-102-1）

Dungeon 层间过渡：卸载上一层模块 → 加载下一层模块（异步，≤2s）
Dungeon ──[死亡/通关]──> Result（叠加层，Dungeon 保留在内存中）
Result ──[再来一局]──> 重置运行时数据 → 重新生成第 1 层（≤5s）
Result ──[返回大厅]──> 异步加载 Lobby → 卸载 Dungeon
```
